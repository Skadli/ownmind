# 005 上下文管理

- 状态：提议
- 日期：2026-10-15

## 问题
agent 每次请求模型时要放进哪些内容、超出上下文窗口怎么办、跨会话靠什么延续、如何利用供应商的提示缓存。

## 决定
1. **单一来源**：会话全文存在 conversation 模块（Rust）。agent 无状态，每次请求前通过 pi 的 `prepareRequest` 调 RPC `context.build(conversation_id)` 取上下文，由 runtime 模块组装。
2. **分层组装（从稳定到易变，利于提示缓存）**：
   1. 系统提示：身份与规则（随版本发布）
   2. 工具声明
   3. 技能索引：每个技能只放名字和一句描述；需要时 agent 用读文件工具读 SKILL.md（按需加载）
   4. 核心记忆：主人资料与长期偏好，限 2k token，agent 用记忆工具改
   5. 最近一次压缩摘要（如有）
   6. 摘要之后的原始消息
   7. 易变信息放最后的系统片段：当前时间、时区
3. **工具输出限额**：单次工具结果超过 8k token 时截断，全文写入沙盒 `/workspace/.outputs/<id>`，结果里给路径，agent 可分段读。
4. **旧工具结果瘦身**：超过最近 10 轮的工具结果，在组装时替换为一行占位（工具名 + 路径），原文仍在库里。
5. **压缩**：估算 token 超过模型窗口 70% 时，runtime 让 agent 调用当前模型把较早部分总结成结构化摘要（目标、已做决定、产出文件、未完成事项），保留最近 6 轮原文；摘要存 conv_compaction。界面仍显示完整历史。
6. **跨会话**：会话之间互不可见，只通过记忆延续。记忆两层：核心记忆（每次都带）+ 记忆条目（用 SQLite FTS5 检索，agent 按需搜索；向量检索以后再加）。
7. **定时任务**：每个定时任务有自己的固定会话，每次触发在其中追加一次运行，任务说明放在该会话的首条系统片段。
8. **缓存**：供应商 sessionId 用会话 ID；第 1–4 层内容变化时才失效缓存。

## 考虑过的方案（及放弃原因）
- agent 端保存会话（pi-coding-agent 的 JSONL）：数据有两个主人，重启丢状态。
- 只做滑动窗口截断：长任务会丢掉早期决定。
- 全部记忆每次都塞进上下文：浪费 token，记忆一多就超窗。
- 一开始就上向量库：单人数据量小，FTS5 够用，少一个依赖。

## 后果
需要 token 估算（以供应商返回的 usage 为准，缺失时按字符估算）；压缩会额外消耗一次模型调用；RPC 协议需包含 context.build 与 compact。
