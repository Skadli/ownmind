
# 数据建模

> 文中的表名、业务名词只是举例，不代表当前项目。

数据上线后最难改。目标是让每张表有唯一主人、关系清楚、命名与 GLOSSARY 一致，并能长期演进。

## 先读
docs/GLOSSARY.md、docs/architecture.md 的“数据”一节、相关模块的 module.yaml。

## 归属
- 每张表只属于一个模块，登记在该模块 module.yaml 的 `owns_tables`。只有 owner 模块能写；其他模块通过 owner 的 api 读写。
- 表名前缀 = 模块前缀（如 `sys_`、`ord_`），一眼看出归属。
- 一个概念放哪个模块拿不准时，放进“对它的生命周期负责”的那个模块。

## 关联
| 情况 | 做法 |
|---|---|
| 模块内一对多 | 子表存父 ID，建数据库外键，按需级联 |
| 模块内多对多 | 关联表 `<前缀>_<a>_<b>`，复合唯一约束，两列都建外键 |
| 跨模块引用 | 只存对方 ID，**不建外键**；需要的冗余展示字段（如名称）显式标为快照，并通过对方的领域事件更新或接受过期 |
| 树（部门、分类） | `parent_id` + 祖先路径列（如 `ancestors` 或 `path`），查子树不递归 |
| 多态引用（附件属于任意实体） | `owner_type` + `owner_id`，加复合索引；不要为每种类型各建一列 |
| 一对一扩展 | 主键即外键的扩展表，只在主表过宽或权限不同时拆 |

为什么跨模块不建外键：迁移可以按模块独立执行，模块可以单独删除或拆成服务，不会出现 A 模块的迁移被 B 模块的表卡住。代价是一致性要靠代码维护，所以对方模块删除实体时要发事件，或者禁止删除只允许停用。

## 标准列
按需使用，不要每张表全加：
- `id`：全项目统一一种（推荐 bigint 雪花 ID 或 UUIDv7，二选一写进决策记录）。
- `tenant_id`：开启多租户时，所有租户数据表必须有，且进入所有唯一约束和主要索引。
- `created_at`、`created_by`、`updated_at`、`updated_by`：业务表默认有。时间统一存 UTC（带时区类型）。
- `deleted_at`：**只在业务需要恢复或审计时**用软删除；其他直接删除。软删除表的唯一约束要考虑已删除行。
- `version`：只在存在并发编辑的表上做乐观锁。

## 命名与类型
- snake_case；列名使用 GLOSSARY 中的词，禁用同义词。
- 金额：整数（分）或 decimal，禁止浮点。
- 状态/类型：小而稳定的集合用数据库枚举或 check 约束；需要运营配置的用字典表。
- 布尔列用 `is_` / `has_` 开头。
- JSON 列只放不参与查询和约束的扩展属性。

## 索引
- 外键列、常用过滤列、排序列建索引。
- 业务唯一性必须用唯一约束表达（如 `tenant_id + code`），不能只靠代码检查。
- 不为假想查询建索引；慢查询出现后再加。

## 文档
- docs/architecture.md 的“数据”一节 维护逻辑模型（mermaid erDiagram，按模块分节）。
- 物理 schema 以迁移为准；ER 图尽量由脚本从数据库生成，避免手写两份。

## 完成标准
- 新表已登记 owner，命名符合前缀和 GLOSSARY
- 关联方式符合上表；跨模块无外键
- 业务唯一性有约束
- 有对应迁移（交给 aef-data）

## 不要做
- 不在项目早期分库分表、读写分离；数据量逼近单表上限前写决策记录再做。
- 不建“万能表”（entity/attribute/value 结构）。
- 不让两个模块写同一张表。
