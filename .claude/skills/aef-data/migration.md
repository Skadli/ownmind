
# 迁移与种子数据

> 文中的表名、业务名词只是举例，不代表当前项目。

schema 只能通过迁移改变。目标：空库能从零建好，旧版本能升级到新版本，生产升级不停机、可恢复。

## 目录（逻辑结构示例；真实路径、命名格式与工具以 docs/stack.md 为准）
```
modules/<m>/migrations/
  V<yyyyMMddHHmm>__<描述>.sql     # 结构变更，按时间戳排序
  R__<描述>.sql                   # 可重复执行的参考数据（幂等 upsert）
db/
  init/                           # 首次初始化（首个管理员等），只执行一次
  demo/                           # 演示数据，仅开发与演示环境
```
迁移工具在 aef-stack 中与用户一起选定（Flyway、Liquibase、golang-migrate、Atlas、Prisma Migrate 等都可以）。多个模块的迁移由同一个迁移运行器按版本号全局排序执行。

## 种子数据分三类
| 类别 | 例子 | 何时运行 | 要求 |
|---|---|---|---|
| 参考数据 | 字典、权限点、菜单、默认角色 | 每次部署 | 幂等 upsert；以代码或 module.yaml 为唯一来源 |
| 初始化数据 | 首个超级管理员、默认租户 | 仅空库首次 | 密码与账号来自环境变量或首次启动生成，**绝不写死在仓库里** |
| 演示数据 | 示例订单、示例用户 | 仅开发/演示 | 生产配置下禁止运行 |

权限点与菜单：在 module.yaml 中声明，由参考数据迁移同步到数据库。不要让数据库里的菜单成为唯一来源，否则代码和数据会漂移。

## 首次部署（空库）
1. 创建数据库与账号（基础设施脚本或部署文档）。
2. 运行迁移运行器：执行全部结构迁移 → 参考数据 → 初始化数据。
3. 启动应用，健康检查确认 schema 版本与代码期望一致。
一条命令完成上面 2–3 步（如 `make db-init` 或部署流水线中的独立任务）。不要用导入 SQL 备份的方式初始化。

## 修改已有结构：expand–contract
破坏性变更（删列、改名、改类型、拆表）分三次发布：
1. **expand**：加新列/新表，代码同时写新旧两处，回填历史数据。
2. **migrate**：代码改为只读新处，确认无流量读旧处。
3. **contract**：删除旧列/旧表。
每一步都要兼容上一版本的代码，因为生产升级时新旧代码会短暂共存。

## 生产升级
- 迁移是部署流水线中的独立步骤：**先迁移，后发版**。开发环境可以在启动时自动迁移，生产不要。
- 大表加索引用数据库的在线方式（如 `CREATE INDEX CONCURRENTLY`）；大批量回填分批执行。
- 有破坏性风险的迁移前先备份；回滚靠向前修复 + 备份恢复，不依赖 down 脚本。

## 门禁（由 aef-gates 实现）
- 已合并的迁移文件内容不可修改（比对哈希）。
- CI 在空的数据库容器中从零跑完全部迁移与参考数据。
- CI 从上一个发布版本的 schema 升级到当前版本。
- 结构迁移中出现 DROP、RENAME、类型变更时必须引用一条 expand–contract 票或决策记录。
- 演示数据在生产配置下不可被加载。

## 完成标准
- 迁移在空库和升级路径上都通过
- 新表登记在 owner 模块的 `owns_tables`
- 参考数据幂等（连续执行两次结果不变）
- 升级说明中写明本次迁移及是否需要停机

## 不要做
- 不修改已合并的迁移；写一个新迁移修正它。
- 不在迁移中调用业务代码（业务代码会变，迁移不会）。
- 不在一个迁移里同时做结构变更和大批量数据回填。
