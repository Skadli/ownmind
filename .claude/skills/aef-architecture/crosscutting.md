
# 横切能力

> 文中的表名、业务名词只是举例，不代表当前项目。

只在项目需要时读。适用于有用户体系的业务系统，工具、库、游戏等项目大多数条目都是“不做”。目标：每项能力有一个明确的结论和唯一的实现位置，业务模块用起来只需一行声明。

## 在 phase-01 逐项给结论
| 能力 | 需要回答的问题 | 推荐默认 |
|---|---|---|
| 认证 | 会话还是令牌？是否需要单点登录、第三方登录？ | 短期访问令牌 + 刷新令牌；第三方登录做成插件 |
| 授权 | 权限粒度？ | RBAC：权限点在 module.yaml 声明，接口用注解/中间件声明所需权限 |
| 数据权限 | 按部门、本人、自定义范围？ | 在数据访问层统一拦截注入条件，业务代码不手写过滤 |
| 多租户 | 要不要？隔离级别？ | 不需要就不做；需要时用共享表 + tenant_id + 统一拦截，写进决策记录 |
| 审计日志 | 记录哪些操作？保留多久？ | 写操作统一切面记录：谁、何时、什么、前后差异 |
| 配置与环境 | 有哪些环境？配置放哪？ | dev/test/staging/prod；配置走环境变量，启动时校验，错就失败 |
| 密钥 | 存在哪？ | 环境变量或密钥管理服务；仓库中只有示例文件 |
| 文件存储 | 本地还是对象存储？ | 先本地，接口留给对象存储；有第二个实现才抽缝 |
| 缓存 | 缓什么？怎么失效？ | 只缓读多写少的数据；写操作负责失效；不缓权限判断结果以外的敏感数据 |
| 异步与定时 | 用什么跑？失败怎么办？ | 任务幂等、可重试、有死信或失败记录 |
| 通知 | 站内、邮件、短信？ | notify 模块统一出口，模板化 |
| 国际化 | 要不要？ | 要就从第一天开始：文案进资源文件，门禁禁止硬编码 |
| 前端菜单路由 | 由谁决定？ | 后端按权限返回菜单，前端动态注册路由 |
| API 契约 | 前后端怎么对齐？ | OpenAPI 为准，前端类型由它生成；契约差异进门禁 |
| 可观测性 | 日志、指标、追踪？ | 结构化日志带请求 ID；健康检查与就绪检查；关键指标 |

## 实现原则
- 横切能力放在平台模块或框架层，业务模块通过声明使用（注解、中间件、配置），而不是复制代码。
- 每项能力在 docs/architecture.md 有一句话结论和实现位置；改变结论写决策记录。
- 不需要的能力不做（比如单租户系统不预留 tenant_id）。

## 完成标准
清单每项都有“做/不做 + 怎么做 + 在哪”的结论。
