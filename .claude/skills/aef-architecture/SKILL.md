# 模块架构

## 目标
模块化单体：每个模块是一个深模块，对外接口小，内部实现隐藏，依赖单向无环。

## 模块形状
```
modules/<name>/
  module.yaml   # 清单（见 .aef/templates/module.yaml；必填四项，其余用到再加）
  api/          # 唯一公共入口：接口、DTO、领域事件
  internal/     # 实现，其他模块不可导入
  migrations/   # 本模块拥有的表
  tests/        # 通过 api 测试
  README.md     # 可选：职责、不变量、常见坑（模块复杂后再写）
```

## 划分方法
1. 从 GLOSSARY 的名词出发，按“谁对它的生命周期负责”聚类。
2. 每个模块能用一句话说清职责；说不清就拆，或者它根本不该是模块。
3. 删除测试：假设删掉这个模块，复杂度消失了（它只是转发）→ 合并掉；复杂度散到多个调用方 → 它值得存在。
4. 依赖方向：业务模块 → 平台模块（system、auth、file…）→ 共享内核（极小：ID、时间、错误类型）。禁止反向和环。
5. 模块之间只通过对方 `api/` 调用，或通过领域事件解耦。事件用于“我做完了，谁关心谁处理”，调用用于“我需要你现在给我答案”。

## 扩展缝
- 平台能力（存储、短信、支付、登录方式、AI 模型）在出现第二个实现时才抽象为“接口 + 注册 + 实现”。
- 一条真正的缝有三方：接口定义、实现方、使用方。只有一个实现的接口是假缝，删掉。

## docs/architecture.md 必须包含
- 模块图（mermaid）与依赖方向
- “新功能放哪”决策表，例如：加业务实体 → 所属模块加垂直切片；加存储方式 → 实现 Storage 接口并注册；加审批流程 → workflow 模块的流程定义
- 横切能力结论（见 aef-architecture（crosscutting.md））

## 完成标准
每个名词有唯一归属；module.yaml 的 depends_on 无环；边界门禁按 module.yaml 生效。

## 不要做
不过早拆微服务；不建“common/utils”大杂烩模块（共享内核保持极小）。

## 横切能力
认证、权限、租户、审计、配置、密钥、文件、缓存、任务、通知、国际化、菜单路由、API 契约、可观测性的逐项清单见 crosscutting.md。只在 phase-01 或新增平台能力时读。
